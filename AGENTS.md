Владелец проекта — OTTO. Основной агент координирует работу и отвечает владельцу по-русски, простыми словами. Прямые указания владельца в текущей переписке имеют приоритет над этими правилами.

- Совместная работа с Claude (решение OTTO 28.10.2026): работа делится по версиям, перекрёстное ревью, метки `claude`/`codex` в Issues — `docs/collaboration.md`. Чужие ветки и PR не трогать.
- Передача от Claude: `docs/handover/2026-10-25.md`. Старые `.claude/agents/` и ссылки на Claude сохраняются как история, но не означают доступ к прежним чатам или общей папке.

## Делегирование

Пользователь поручил создать команду помощников для этого проекта. Для содержательных задач делегируй подходящим специалистам самостоятельные части работы; мелкие однозначные правки выполняй сам. Не запускай весь штат на каждую задачу. Соблюдай доступный предел одновременно работающих агентов.

Настройки ролей находятся в `.codex/agents/`: `pt_analyst`, `pt_designer`, `pt_core`, `pt_frontend`, `pt_qa`, `pt_reviewer`, `pt_release`, `pt_archivist`. Если клиент не загрузил именованные роли, прочитай соответствующий TOML и передай его инструкции обычному помощнику. Не утверждай, что конфигурация уже загружена клиентом, без проверки.

Каждому помощнику дай цель, ветку/коммит, доступные для изменения файлы, критерии готовности и ожидаемый результат. Параллельно можно исследовать и проверять; изменения общих файлов выполняются последовательно. После изменения данных сначала согласуй ядро и контракт команд, затем интерфейс.

Значимые изменения до предложения слияния получает независимый ревьюер, который не был автором исправлений. Помощники возвращают результаты координатору. Новые самостоятельные чаты и сообщения в существующие чаты создаются только по прямому поручению пользователя.

## Инварианты приложения

- Рабочая база — SQLite; суммы хранятся целыми минимальными единицами валюты. Сохраняй правила округления и не переписывай существующие расчёты без задачи.
- UI → `src/lib/api.ts` → команды Tauri → `crates/core`; SQL и финансовая логика находятся в ядре.
- Переводы не являются расходами/доходами. Выдача и возврат основного долга — переводы, проценты — отдельные операции.
- Миграции идут вперёд новым номером; выпущенные миграции не правь. Проверяй сохранность данных старых версий. `app.kazna.desktop` определяет папку данных и не меняется в рамках обычных правок.
- Учитывай бюджетный месяц от выбранного дня, валюты и курсы на нужную дату, расходы событий и последние оценки инвестиций/имущества.
- В 0.17 баланс счёта и распределённый по месяцам расход имеют разные источники расчёта. Проверяй согласованность бюджета, отчётов, тегов, экспорта, групп чеков и отмены.
- Реальную базу пользователя для тестов не открывай на запись. Используй отдельную тестовую папку данных.

## Готовность и полномочия

- Изменения ведутся в отдельной ветке и проходят PR. Версию меняй только при изменении программы; документы и настройка команды сами по себе нового выпуска не требуют.
- Подтверждай ровно те проверки, которые действительно выполнены, с веткой/коммитом. Текст старого отчёта не равен новому прогону. Успешная Windows-сборка не равна проверке сценариев Windows-окна.
- Применяй проверки по изменению: типы/сборка/тесты UI, Rust fmt/clippy/tests, миграции, сквозные сценарии и снимки по необходимости. Для одних документов достаточно проверки ссылок и формата конфигурации.
- Слияние в `main` — после явного «сливай» для соответствующего PR. После разрешённого слияния версии выпуск выполняется по `docs/releasing.md`. Не считай передачу проекта разрешением слить PR №22.
- Удаление существующих пользовательских файлов, веток или данных требует явного согласия. Не переписывай опубликованные теги и выпуски. Не показывай значения секретов и не проси вставлять их в чат.
- Давай прямые ссылки на PR, Actions, артефакты, выпуски и страницы настроек; для кнопки без отдельного адреса — ссылку на страницу и точное название.
- После результата обновляй `docs/project-state.md`; важные новые продуктовые решения — `docs/decisions.md`. Не называй процент готовности без проверяемого основания.

## Ежедневный рабочий цикл

Перед реализацией проверь существующую задачу, владельца файлов и критерии. Сформулируй короткое поручение каждому действительно нужному помощнику. Сначала согласуй атомарный контракт, затем интегрируй ядро и интерфейс; независимые области выполняй параллельно. Проверь исходный дефект и связанные пользовательские сценарии, после чего получи независимое ревью на текущий коммит.

Текущие задачи и критерии ведутся в GitHub Issues, реализация — в соответствующем PR, точка продолжения — в `docs/project-state.md`. Не создавай параллельные дубли очереди. Фиксируй «реализовано», «проверяется» и «выпущено» отдельно. Завершение кода не закрывает непроверенную задачу. Подробный порядок и план ответственности — `docs/work-plan.md`.
