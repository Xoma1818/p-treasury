# Архитектура десктопного приложения для личного бюджета

Версия 1.5 · 2026-10-20 (учтены ответы BOB, ревизия и сверка проекта в [history/reviews-2026-10-20.md](../history/reviews-2026-10-20.md): долги с калькулятором, обновления, Excel, календарь, напоминания, заметки, удобства ввода)

**Что изменилось в 1.5 для схемы этапа 0:** в `accounts` добавлено `opening_date`; `budgets.period_start` теперь хранит фактическую дату начала периода с учётом настройки «первый день месяца» (тип столбца прежний); в `debt_payments` добавлено `recalc_mode` (таблица этапа 4).

Состав функций MVP согласован с [product/mvp-features.md](../product/mvp-features.md): этот документ описывает, *как* устроено приложение, а состав версий берётся оттуда.

## 1. Исходные условия

| Условие | Что из этого следует |
|---|---|
| Только ПК (Windows, macOS, Linux) | Нативное десктопное приложение, без сервера и без мобильной версии |
| Один пользователь, без ролей и общего доступа | Нет аутентификации, нет синхронизации, нет бэкенда. Все данные локально |
| Дизайн: выбран стиль A, экраны в [design/README.md](../design/README.md) | Архитектура отделяет UI от логики, поэтому правки дизайна не трогают ядро |

Принципы, которые из этого вытекают:

1. **Local-first.** Приложение работает полностью офлайн, данные лежат в одном файле на диске пользователя.
2. **Данные принадлежат пользователю.** Файл базы можно скопировать, сделать резервную копию, выгрузить в CSV.
3. **Деньги считаются точно.** Никаких чисел с плавающей точкой для сумм.
4. **Тонкий UI.** Вся бизнес-логика (балансы, бюджеты, повторяющиеся платежи) живёт в отдельном слое и покрывается тестами.

## 2. Стек

### Выбрано: Tauri 2 + React + TypeScript + SQLite

Решение принято 2026-10-20 (BOB доверил выбор стека).

| Слой | Технология | Зачем |
|---|---|---|
| Оболочка | **Tauri 2** | Нативное окно на системном WebView, установщик 5–15 МБ, мало памяти, сборка под Win/macOS/Linux |
| Ядро (backend внутри приложения) | **Rust** + `rusqlite` (SQLite в комплекте) | Доступ к БД, миграции, бизнес-правила, резервные копии |
| UI | **React + TypeScript + Vite** | Самая большая экосистема компонентов и графиков, легко сменить дизайн позже |
| Состояние UI и запросы | TanStack Query (кеш данных из ядра) + Zustand (локальное состояние UI) | Простая модель, без Redux-шаблонов |
| Компоненты | Headless-библиотека (Radix UI / shadcn/ui) | Не навязывает визуальный стиль, дизайн добавится поверх |
| Графики | Recharts или ECharts | Круговые диаграммы по категориям, динамика по месяцам |
| Тесты | `cargo test` для ядра, Vitest для UI, Playwright для сквозных сценариев | |

**Почему рекомендую:** лёгкое и быстрое приложение, SQLite встроен в бинарник, Rust надёжно обрабатывает данные, а UI на веб-технологиях проще всего перерисовать, когда дойдём до дизайна.

**Минус:** два языка (Rust и TypeScript). Если хочется только один язык, подходит первая альтернатива.

### Альтернатива 1: Electron + React + TypeScript + SQLite (`better-sqlite3`)

- Плюсы: один язык (TypeScript) везде, огромная экосистема, проще порог входа.
- Минусы: установщик 80–150 МБ, заметно больше расход памяти.
- Когда выбирать: если разработчик знает только JS/TS и размер приложения не важен.

### Альтернатива 2: .NET 8 + Avalonia UI + SQLite (EF Core)

- Плюсы: полностью нативный UI, один язык (C#), строгая типизация, хорош для «табличных» бизнес-приложений.
- Минусы: меньше готовых UI-компонентов и графиков, дизайн делать дольше.
- Когда выбирать: если разработчик из мира C#/.NET.

## 3. Хранение данных

- **СУБД:** SQLite, один файл `budget.db`.
- **Расположение:** стандартная папка данных приложения ОС (`%APPDATA%\Budget\` на Windows, `~/Library/Application Support/Budget/` на macOS, `~/.local/share/budget/` на Linux). В настройках можно выбрать другой путь (например, папку Dropbox для личной копии).
- **Режим:** `journal_mode=WAL`, `foreign_keys=ON`.
- **Миграции:** нумерованные SQL-файлы, встроенные в приложение, применяются при запуске; версия схемы хранится в `PRAGMA user_version`.
- **Резервные копии:** автоматическая копия файла БД перед каждой миграцией (в папку данных) и **автокопия при закрытии приложения в папку, выбранную пользователем** (например, папку Яндекс.Диска); хранятся последние N копий (по умолчанию 10). Плюс ручная копия и восстановление.
- **Шифрование (не в MVP):** опционально SQLCipher с паролем при запуске.
- **Деньги:** целое число в минимальных единицах валюты (копейки/центы), тип `INTEGER`. Расходы и доходы хранятся с одинаковым знаком суммы, направление задаёт тип операции.
- **Даты:** дата операции как `TEXT` в формате ISO `YYYY-MM-DD`; служебные метки времени в UTC ISO 8601.
- **Идентификаторы:** UUID v7 в `TEXT` (сортируются по времени, не конфликтуют при импорте).

## 4. Модель данных

### Схема связей

```
currencies ─┐
            ▼
accounts ◄──── transactions ────► categories (дерево: parent_id)
   ▲               │  ▲                 ▲
   │               │  └── recurring_rules (порождает операции)
   │               ▼
   │          transaction_tags ──► tags
   │
budgets ──► budget_lines ──► categories

debts ──► accounts (служебный счёт долга)
  │
  ├──► debt_schedule (график платежей)
  │         ▲
  └──► debt_payments ──► transactions (основной долг + проценты)

reminders ──► reminder_occurrences ◄── debt_schedule (напоминания о платежах)
                     │
                     └──► transactions («Создать операцию»)

notes ──► дата / transactions / accounts / debts   (+ notes_fts для поиска)
```

### Долги и займы (MVP)

**Главная идея: каждый долг — это служебный счёт.** При создании долга приложение создаёт счёт типа `debt` в валюте долга, скрытый из списка обычных счетов. Тогда всё движение денег описывается уже существующими операциями:

| Событие | Операция |
|---|---|
| Я дал в долг 20 000 ₽ с «Карты» | `transfer`: «Карта» → счёт долга. Баланс счёта долга +20 000 (мне должны) |
| Я взял кредит 300 000 ₽ на «Карту» | `transfer`: счёт долга → «Карта». Баланс счёта долга −300 000 (я должен) |
| Возврат основного долга | `transfer` в обратную сторону на сумму основного долга |
| Проценты по моему кредиту | `expense`, категория «Проценты по кредитам», счёт оплаты |
| Проценты, которые платят мне | `income`, категория «Проценты по займам», счёт зачисления |

Что это даёт без отдельной логики: остаток долга = баланс служебного счёта; выдача и возврат долга не попадают в расходы, доходы и бюджеты (это переводы); проценты попадают в расходы и доходы как обычные операции; «Чистые активы» = сумма обычных счетов + сумма счетов долгов (положительные — должны мне, отрицательные — должен я), в основной валюте по курсам из `exchange_rates`. Обе категории процентов входят в набор категорий по умолчанию (вместе с доходом «Кешбэк и бонусы»).

| Поле | Тип | Описание |
|---|---|---|
| id | TEXT PK | |
| debt_id | TEXT FK | |
| schedule_id | TEXT FK NULL | Какую строку графика закрывает (пусто для досрочного или внепланового платежа) |
| date | TEXT | |

| recalc_mode | TEXT NULL | Как пересчитан график после частичного или досрочного платежа: `reduce_payment` или `reduce_term` |

Отметка «Оплачено» выполняется в одной транзакции SQLite: создаются 1–2 операции, запись в `debt_payments`, у строки графика меняется статус. Удаление платежа откатывает всё это вместе, включая пересчёт графика.

**Частичный и досрочный возврат.** Если внесена сумма больше или меньше графика, пользователь выбирает, как пересчитать оставшиеся строки `pending` от фактического остатка (оплаченные строки не меняются):
- **уменьшить платёж** (`reduce_payment`, по умолчанию): срок и дата окончания прежние, платёж пересчитывается;
- **уменьшить срок** (`reduce_term`): платёж прежний (для аннуитета) или прежняя часть основного долга (для дифференцированного), число оставшихся платежей сокращается, последний платёж меньше; `maturity_date` обновляется.

Для разового возврата выбора нет: уменьшается остаток к возврату в конце срока.

| debt_schedule_id | TEXT FK NULL | Для `debt` |
| scheduled_at | TEXT | Когда должно сработать |
| status | TEXT | `pending`, `done`, `snoozed`, `dismissed` |
| snoozed_until | TEXT NULL | Для «Отложить» |
| notified_at | TEXT NULL | Когда показано системное уведомление |
| completed_at | TEXT NULL | |
| transaction_id | TEXT FK NULL | Операция, созданная кнопкой «Создать операцию» |

Уникальный ключ `(source, reminder_id, debt_schedule_id, scheduled_at)`. Строка создаётся, когда срабатывание наступило или пользователь с ним что-то сделал; до этого оно существует только как вычисленная дата.

**Напоминания о платежах по долгам** не заводятся вручную: для каждой строки `debt_schedule` со статусом `pending` срабатывание вычисляется как `due_date − N дней` (N из настройки `debt_reminder_days_before`, по умолчанию 3). «Создать операцию» для такого напоминания открывает отметку платежа по долгу, а не обычную форму операции.

**notes** — заметки
| Поле | Тип | Описание |
|---|---|---|
| id | TEXT PK | |
| body | TEXT | Текст |
| date | TEXT NULL | День календаря |
| transaction_id, account_id, debt_id, budget_id | TEXT FK NULL | Необязательная привязка (не больше одной): операция, счёт, долг или месяц бюджета |
| created_at, updated_at | TEXT | |

Поиск по заметкам: полнотекстовый индекс SQLite FTS5 (`notes_fts`, поддерживается рус. язык через токенизатор `unicode61`), обновляется триггерами. При удалении операции, счёта или долга заметка остаётся, а привязка очищается.

**Календарь** собственной таблицы не имеет: модуль `calendar` собирает для каждого дня месяца суммы операций (в основной валюте), строки графиков долгов, срабатывания напоминаний и заметки одним запросом на месяц.

**settings** — ключ-значение: основная валюта (по умолчанию RUB), первый день месяца, формат даты, путь к БД, за сколько дней напоминать о платежах по долгам, сворачивать ли в трей при закрытии, папка автокопий и сколько копий хранить, режим «скрыть суммы».

**exchange_rates** (MVP) — курсы для пересчёта в основную валюту в отчётах и общем балансе: `date, from_code, to_code, rate, source` (`manual` или `cbr`). Курс вводится вручную или подставляется последний известный; с версии 0.9 курсы ЦБ РФ загружаются по кнопке (`source = cbr`, модуль `cbr.rs`; единственный сетевой запрос приложения кроме проверки обновлений).

Разделы меню повторяют дизайн: «Бюджет» (а не «Бюджеты»); калькулятор открывается внутри раздела «Займы и долги»; напоминания показываются в «Календаре» и на «Главной», отдельного пункта меню у них нет. Модули ядра от этого не зависят.

Правило границ: UI вызывает только команды ядра и никогда не пишет SQL; модули ядра обращаются к БД только через `storage`. Благодаря этому смена дизайна не затрагивает логику, а логику можно тестировать без UI.

### Ключевые сценарии

- **Запуск приложения:** открыть БД → применить миграции (с резервной копией) → показать «Главная». С версии 2 здесь же `recurring` показывает платежи к подтверждению.
- **Добавление расхода:** форма → команда `create_transaction` → валидация (счёт активен, категория типа `expense`, сумма > 0) → запись → UI обновляет баланс и бюджет через инвалидацию кеша.
- **Перевод между счетами:** одна запись `transfer` с `account_id` и `to_account_id`; не влияет на бюджеты и отчёты по расходам.

### Логика калькулятора (`loan_calc`)

Вход: сумма `P`, ставка годовых `R`, срок `n` месяцев, вид погашения, дата выдачи и первого платежа. Выход: строки графика (дата, платёж, основной долг, проценты, остаток) и итоги (первый и последний платёж, сумма выплат, переплата).

- Месячная ставка `r = R / 12`. Расчёт ведётся в десятичных числах (`rust_decimal`), а каждая сумма в строке округляется до копейки по правилу «половина вверх».
- **Аннуитет:** платёж `A = P · r / (1 − (1 + r)^−n)`, округлённый до копейки. В каждой строке проценты = остаток · `r`, основной долг = `A` − проценты.
- **Дифференцированный:** основной долг в каждой строке `P / n`, проценты = остаток · `r`, платёж = их сумма (первый платёж самый большой).
- **Разовый возврат:** одна строка в дату погашения: основной долг `P` + проценты `P · R · дни / 365` (или 0 для беспроцентного долга).
- **Ставка 0 %:** аннуитет и дифференцированный совпадают, платёж `P / n`.
- **Последняя строка** забирает накопленную ошибку округления, чтобы остаток стал ровно 0.
- **Сравнение:** калькулятор строит оба варианта (аннуитет и дифференцированный) на одних условиях и показывает их рядом. «Сохранить как долг» передаёт те же параметры в `debts`.
- Упрощение MVP: проценты за месяц считаются как `r` от остатка независимо от числа дней в месяце; банк может считать по дням, поэтому возможна разница в несколько рублей. При отметке платежа сумму можно поправить вручную.

Контрольный пример для тестов (из описания функций): 300 000 ₽, 18 %, 24 месяца, аннуитет → платёж 14 977,23 ₽, переплата ≈ 59 453 ₽; дифференцированный на тех же условиях → переплата 56 250 ₽.

### Удобство работы (отдельные модули)

Эти функции сделаны отдельными модулями поверх ядра: их можно выпустить в MVP или перенести в версию 2, не меняя остальную архитектуру.

**Отмена и повтор (Ctrl+Z / Ctrl+Y), модуль `undo`**
- Все записи в БД идут через `storage`, поэтому он может для каждого действия пользователя сохранить «снимок до» и «снимок после» затронутых строк.
- Одно действие = одна запись журнала, даже если оно меняет несколько таблиц (например, отметка платежа по долгу: две операции, `debt_payments` и строка графика).
- Отмена применяет «снимок до» в одной транзакции SQLite, повтор применяет «снимок после». Перед отменой проверяется, что строки не изменились позже; если изменились, отмена этого шага не выполняется и приложение говорит об этом.
- Журнал хранится в памяти, до 50 шагов, и очищается при закрытии приложения. Новое действие после отмены стирает ветку повтора.

**Горячие клавиши.** Один реестр сочетаний в UI (React): Ctrl+N новая операция, Ctrl+T новый перевод, Ctrl+F поиск, Ctrl+1…9 разделы, Ctrl+Enter сохранить форму, Ctrl+Z / Ctrl+Y. Это сочетания внутри окна, не глобальные для всей ОС. Справка по клавишам строится из того же реестра.

**Режим «скрыть суммы».** Все суммы в интерфейсе выводит один компонент `Money`; при включённом режиме он показывает «•••». Режим хранится в `settings` и переключается одной кнопкой или клавишей. На выгрузку в Excel режим не влияет.

**Арифметика в поле суммы.** Поле принимает `250+180`, `1500*3`, `(1200-200)/2`. Выражение разбирает маленький парсер в UI (только числа, `+ − * /` и скобки, без выполнения кода), результат округляется до копейки и показывается рядом с полем до сохранения.

**«Можно тратить сегодня»** (модуль `budgets`): (сумма лимитов расходов в бюджете текущего бюджетного месяца − фактические расходы по этим категориям) / число оставшихся дней до конца бюджетного месяца (по настройке «первый день месяца»), включая сегодня. Если бюджета на месяц нет, показатель не выводится. Отрицательное значение показывается как перерасход.

**Норма сбережений** (модуль `reports`): (доходы − расходы) / доходы за период, в основной валюте. Переводы, в том числе выдача и возврат основного долга, не учитываются, проценты по долгам учитываются. Показывается в отчётах, на «Главной» и на листе «Сводка» в Excel.

### Уведомления и работа в трее

- **Системные уведомления:** `tauri-plugin-notification` показывает обычные уведомления Windows, macOS и Linux. Нажатие на уведомление открывает окно приложения на этом напоминании с кнопками «Выполнено», «Отложить», «Создать операцию». Кнопки прямо внутри системного уведомления на ПК работают неодинаково в разных ОС, поэтому в MVP действия выполняются в окне приложения.
- **Трей:** иконка в системном трее (встроенный `tray-icon` в Tauri 2) с меню «Открыть», «Добавить операцию», «Выход». Закрытие окна по умолчанию сворачивает приложение в трей, чтобы напоминания продолжали приходить; это отключается в настройках.
- **Автозапуск (версия 2):** `tauri-plugin-autostart`, по умолчанию выключен; включается в настройках, чтобы напоминания приходили сразу после включения компьютера.
- **Планировщик:** асинхронная задача в ядре (Rust, `tokio`) спит до ближайшего срабатывания (но не дольше минуты, чтобы учесть изменения и выход компьютера из сна), затем показывает уведомление и ставит `notified_at`.
- **Пропущенные:** при запуске планировщик находит срабатывания с датой в прошлом без `notified_at` и без `completed_at` и показывает одно окно «Пропущенные напоминания» вместо пачки уведомлений.
- Когда приложение полностью закрыто, уведомлений нет; это ограничение MVP, и оно же записано в описании функций.

### Выгрузка сводки в Excel

- Формат `.xlsx`, библиотека `rust_xlsxwriter` (без установленного Excel, файл открывается в Excel, LibreOffice и Google Таблицах).
- Пользователь выбирает период (месяц, квартал, год, произвольный) и получает одну книгу с листами:
  - **Сводка:** доходы, расходы, сальдо, норма сбережений, корректировки отдельной строкой, остатки счетов на начало и конец периода, «Чистые активы»;
  - **По категориям:** расходы и доходы по категориям и подкатегориям, доля в процентах;
  - **Бюджет:** план, факт и отклонение по категориям за каждый месяц периода;
  - **По месяцам:** доходы, расходы и сальдо помесячно;
  - **Долги:** остаток по каждому долгу и ближайшие платежи;
  - **Операции:** все операции периода с датой, счётом, категорией, суммой в валюте счёта и в рублях.
- Состав листов совпадает с планом функций и диалогом выгрузки в дизайне.
- **Выгрузка текущего экрана:** список операций с текущими фильтрами или открытый отчёт выгружается в `.xlsx` (один лист) или CSV той же функцией записи, что и сводка.
- Суммы пишутся числами с денежным форматом, даты настоящими датами Excel, поэтому по ним сразу работают фильтры, сортировка и формулы.
- Для CSV-экспорта: кодировка UTF-8 с BOM и разделитель `;`, чтобы русская версия Excel открывала файл двойным щелчком без «кракозябр».

### Обновления и расширяемость

**Обновление приложения**
- Встроенный механизм Tauri (`tauri-plugin-updater`): при запуске (и по кнопке в настройках) приложение проверяет файл с описанием последней версии, показывает, что нового, и по согласию пользователя скачивает и ставит обновление. Можно отключить автоматическую проверку.
- Пакеты обновлений подписываются ключом разработчика; приложение ставит только пакет с верной подписью.
- Версии по схеме SemVer (`1.4.2`). Где хранить релизы (GitHub Releases или свой статический сервер) решим при первой публикации; приложение знает только адрес файла с описанием версии.

**Безопасное обновление данных**
- Перед применением миграций автоматически делается копия файла БД.
- Каждая миграция выполняется в транзакции SQLite; при ошибке изменения откатываются, приложение сообщает об ошибке и продолжает работать на копии.
- Миграции только «вперёд» и только добавляющие: новые таблицы и столбцы со значениями по умолчанию. Столбцы не удаляются и не переименовываются в той же версии, где перестают использоваться.
- Если файл БД создан более новой версией приложения (`user_version` больше известной), старая версия не открывает его на запись и предлагает обновиться.
- Резервные копии и выгрузка в JSON содержат номер версии схемы, поэтому копию из старой версии можно восстановить в новой: она проходит те же миграции.

**Место для новых функций**
- Каждая область (счета, бюджеты, долги и т. д.) — отдельный модуль ядра со своими командами и своими таблицами; новая функция добавляется новым модулем и новой миграцией, не трогая существующие.
- В схему заранее заложены поля и таблицы для версии 2 (повторяющиеся платежи, теги, разбивка операции), см. раздел 4.
- Флаги функций в `settings` позволяют включать новые разделы постепенно.

## 6. План MVP

### Этап 0. Каркас
- Проект Tauri + React + TypeScript, сборка под Windows (основная платформа) и проверка на macOS/Linux.
- Модуль `storage`: SQLite, миграции, первая схема.
- Простейший UI-каркас: боковое меню и пустые экраны, без дизайна.
- Механизм миграций с резервной копией и откатом; проверка версии схемы при открытии файла.

### Этап 1. Учёт (ядро MVP)
- Счета: создание, редактирование, архив, начальный остаток и дата начала учёта, баланс, корректировка баланса; валюта у каждого счёта.
- Мультивалютность: справочник валют, курсы (ручной ввод), переводы между счетами в разных валютах (`amount` + `to_amount`), общий баланс и отчёты в основной валюте.
- Категории: двухуровневое дерево, набор по умолчанию, перенос операций при удалении категории.
- Операции: расход, доход, перевод; список с фильтрами по периоду, счёту, категории и типу; поиск; подстановка последних счёта и категории.
- Главная: общий баланс, балансы счетов, кратко бюджет месяца, последние операции (ближайшие платежи по долгам добавляются на этапе 4).

### Этап 2. Бюджеты
- Месячный бюджет с лимитами по категориям; период считается от настройки «первый день месяца».
- План/факт/остаток, отметка перерасхода.
- Копирование бюджета из прошлого месяца.

### Этап 3. Отчёты
- Расходы по категориям (диаграмма и таблица), доходы и расходы по месяцам, остатки счетов на дату.
- Выбор периода и переход из отчёта к списку операций.

### Этап 4. Долги и займы
- Модуль `loan_calc` с тестами на все виды погашения, округление и контрольный пример.
- Калькулятор: ввод условий, график, переплата, сравнение аннуитета и дифференцированного, «Сохранить как долг».
- Долги: создание (дал/взял) со служебным счётом, график, отметка платежа с созданием операций, частичный и досрочный возврат с пересчётом графика (выбор «уменьшить платёж» или «уменьшить срок»), закрытие.
- Раздел «Займы и долги»: сводка «должны мне / должен я», карточка долга, просрочки, ближайшие платежи; «Чистые активы» и ближайшие платежи на «Главной».

### Этап 5. Календарь, напоминания и заметки
- Функция `expand` для повторов с тестами (конец месяца, високосный год, перевод часов).
- Напоминания: создание, повторы, «Выполнено», «Отложить», «Создать операцию»; напоминания о платежах по долгам.
- Планировщик, системные уведомления, трей, окно пропущенных напоминаний.
- Заметки с привязкой и поиском; заметки в карточках операции и долга.
- Календарь: вид месяца и недели, карточка дня, итог месяца; ближайшие напоминания на «Главной».

### Этап 6. Данные и настройки
- Выгрузка сводки за период в Excel (`.xlsx`), 6 листов; выгрузка списка операций с фильтрами или текущего отчёта в Excel или CSV.
- Экспорт CSV (UTF-8 с BOM, разделитель `;`), импорт CSV по шаблону с предпросмотром ошибок.
- Резервная копия в файл и восстановление; автокопия при закрытии в выбранную папку с хранением N копий; напоминание о копии, если автокопия выключена. Копия делается через SQLite backup API во временный файл с последующим переименованием, чтобы в облачную папку не попала недописанная копия.
- Настройки (основная валюта, начало месяца, формат даты).
- Обновление приложения: подписанные пакеты, проверка новой версии при запуске и по кнопке.

### Этап 7. Удобство работы (отделяемый)
Порядок этапов 0–6 не меняется; этот этап можно целиком или по пунктам перенести в версию 2.
- Шаблоны операций и подсказка категории по получателю.
- Арифметика в поле суммы.
- Горячие клавиши и справка по ним.
- Отмена и повтор (журнал `undo`).
- Режим «скрыть суммы».
- «Можно тратить сегодня» на «Главной» и в бюджете, норма сбережений в отчётах, на «Главной» и в Excel.
- Тип счёта «кредитная карта» с лимитом и доступным остатком, доход «Кешбэк и бонусы» в наборе категорий, заметки к месяцу бюджета (поля и таблицы для этого есть в схеме с этапа 0).

**MVP готов** после этапов 0–7: можно вести счета, записывать операции, планировать месячный бюджет, смотреть отчёты и выгружать сводку в Excel, вести долги и кредиты с графиком платежей, видеть всё в календаре, получать напоминания и вести заметки, переносить данные из Excel, обновлять приложение и не бояться потерять данные, а ввод операций занимает пару нажатий.
