# Обновление Kazna с 0.42.8 до 0.43.0 через настройки

**Проверка прошла 27 ноября 2026 года.** Установленная Kazna 0.42.8 нашла выпуск 0.43.0 через «Настройки → О программе → Проверить обновления». После нажатия «Обновить» приложение создало резервную копию, установило выпуск и самостоятельно открыло новое окно. Все семь операций, остатки трёх счетов и 48 настроек вымышленного бюджета сохранились. [Прогон Windows 11](https://github.com/Xoma1818/p-treasury/actions/runs/45909468120) · [Архив со снимками, журналом процессов и четырьмя копиями SQLite](https://github.com/Xoma1818/p-treasury/actions/runs/45909468120/artifacts/15159084479).

## Как подтверждён перезапуск

1. На чистой виртуальной машине Windows 11 Enterprise ARM64, сборка 26200, установили официальный x64-выпуск 0.42.8. Приложение работало под эмуляцией x64, с отдельными базой, профилем WebView2 и каталогом для резервных копий. Перед обновлением прочитали журнал, счета и настройки из работающего приложения и сохранили снимок SQLite. [Исходный выпуск](https://github.com/Xoma1818/p-treasury-releases/releases/tag/v0.42.8).
2. В окне 0.42.8 нажали «Проверить обновления», затем «Обновить». В 02:16:14 МСК скачанный самой Kazna установщик совпал с опубликованным файлом по SHA-256. Журнал Windows записал цепочку процессов: Kazna 0.42.8 (PID 4220) запустила установщик (PID 5376), а тот запустил новую Kazna (PID 8832). [Предложение обновления в 0.42.8](../design/screens/update-0428-0430-before-offer.png) · [Целевой выпуск](https://github.com/Xoma1818/p-treasury-releases/releases/tag/v0.43.0).
3. У нового процесса зафиксировали главное окно «Kazna» (HWND 786520). Реестр Windows и файл в прежней папке установки показали версию 0.43.0. Пока это окно работало, сняли вторую копию той же базы. Затем штатно закрыли окно и повторно открыли установленную 0.43.0 для сверки через интерфейс и снимков. [Экран с установленной версией 0.43.0](../design/screens/update-0428-0430-after-settings.png).
4. Сравнили четыре состояния базы: до обновления, в автоматически открывшемся окне, после повторного открытия и в резервной копии, созданной самой Kazna перед установкой. Во всех четырёх совпали схема 32, столбцы и строки всех 53 прикладных таблиц. Проверки целостности SQLite и внешних ключей прошли на каждой копии. [Сценарий проверки и сверки](https://github.com/Xoma1818/p-treasury/tree/63c33a3784d32d68aac0d52f2df5af346dd00c6f/qa/inapp-0428-0430).

| Проверенный файл | SHA-256 |
|---|---|
| Установщик, скачанный приложением | `600bf54566d3288b55d248935d8eee58f4b0d3dae5b05b3ab94314240ee9adca` |
| Установленный Kazna.exe 0.43.0, совпадает с файлом из официального установщика | `62691fd11b4667906b7ec4ce7c6dd09715d1fe287a7d9fc865a40fa0cebc1ec9` |

В первой попытке драйвер завершили сразу после выхода старого процесса. За 150 секунд проверка не обнаружила нового окна, и до сверки данных дело не дошло. В повторном прогоне драйвер оставили работающим и отдельно записали запуск установщика и нового окна. Все результаты и снимки выше относятся к этому повторному прогону.
