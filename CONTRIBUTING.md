# Как работать с P-Treasury

Начните с [текущего состояния](docs/project-state.md) и [рабочего плана](docs/work-plan.md). История изменений — [CHANGELOG](CHANGELOG.md), принятые ограничения — [решения владельца](docs/decisions.md).

## Ошибка или предложение

Откройте [новую задачу](https://github.com/Xoma1818/p-treasury/issues/new/choose). Для ошибки нужны версия, шаги, ожидаемый и фактический результат; для идеи — пользовательская задача и критерий пользы. Идея не считается согласованной функцией до решения владельца.

## Изменение

1. Найдите существующую задачу; не создавайте дубль. Укажите ответственного специалиста и критерии готовности.
2. Работайте в отдельной ветке. Для новых веток команды используйте `codex/<краткая-тема>`; существующие ветки и ссылки сохраняйте.
3. Меняйте только согласованный объём. Общие файлы имеют одного автора, контракт ядра и интерфейса согласуется до интеграции.
4. Проверьте изменение по его риску. Финансовые расчёты, миграции и составные действия требуют проверки данных и отмены. Для документов достаточно ссылок и формата.
5. Откройте или обновите существующий PR со ссылкой на задачу, результатом и фактическими проверками. После исправления ошибка остаётся открытой до интеграции проверенного изменения.
6. Получите независимое ревью на текущий коммит. Слияние в `main` выполняется после разрешения владельца, выпуск — по [правилам](docs/releasing.md).

## Проверки

- Интерфейс: типы, подходящие Vitest-тесты и сборка.
- Ядро: формат, clippy, тесты и значимые граничные сценарии.
- Схема: обновление поддерживаемой базы, сохранность связей, копия и восстановление.
- Настоящее окно: важные пользовательские сценарии, темы и размеры, когда меняется UI.

Результат указывается с коммитом и средой. «Не запускалось» и «пропущено» не заменяются словом «пройдено». Успешная сборка Windows не подтверждает поведение установленного окна.

## Порядок в GitHub

- Issues — очередь и критерии; метки `bug`, `enhancement`, `documentation`.
- PR — реализация и доказательства. Один PR на связанную задачу, без параллельных дублей.
- CHANGELOG — результат для пользователя, без внутренних отчётов команды.
- `docs/project-state.md` — короткая точка продолжения, а не копия всей истории.
- Секреты остаются в настройках GitHub, данные пользователя не используются как тестовые.
