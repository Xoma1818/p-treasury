# Тестирование «Казны»

Принцип: **каждый шаг заканчивается зелёной проверкой**. Шаг не считается сделанным, пока `scripts/check.sh --e2e` не проходит целиком. Найденная ошибка сначала получает тест, который её ловит, и только потом исправляется, чтобы она не вернулась.

## Одна команда проверки

```bash
npm run check        # формат, линтеры, все тесты ядра и UI, сборка (около минуты)
npm run check:e2e    # то же плюс сквозные тесты на настоящем окне приложения
```

Что входит:

| Шаг | Что ловит |
|---|---|
| `cargo fmt --check`, `cargo clippy -D warnings` | Небрежный и подозрительный код ядра |
| `cargo test` | Логику ядра: деньги, курсы, балансы, бюджеты, долги, напоминания. Тесты работают с настоящим файлом SQLite, не с заглушками |
| `tsc --noEmit` | Ошибки типов в интерфейсе, расхождение типов UI и команд ядра |
| `vitest` | Логику интерфейса: формат сумм, арифметика в поле суммы, формы |
| `vite build` | Интерфейс собирается |
| Сквозные тесты (`e2e/`) | Настоящее окно Tauri через WebDriver (`tauri-driver`), каждый прогон с чистой папкой данных: нажимаем кнопки как пользователь и проверяем, что видно на экране и что записалось в базу |

## Уровни тестов

1. **Модульные (ядро, Rust).** Каждая функция с правилами: перевод между валютами, пересчёт по курсу, округление, баланс счёта, перенос операций при удалении категории, график кредита. Граничные случаи обязательны: ноль, отрицательный остаток, 31-е число в феврале, високосный год, валюта без копеек (иена).
2. **Свойства (property-based, `proptest`).** Для денег и калькулятора кредита: на тысячах случайных входов сумма платежей = долг + проценты, остаток в конце ровно 0, формат и разбор суммы обратимы.
3. **Интеграционные (ядро + SQLite).** Цепочки действий через команды ядра на файле базы: создать счета → операции → баланс; отметить платёж по долгу → две операции + строка графика; отмена Ctrl+Z возвращает базу в точности к прежнему состоянию.
4. **Тесты интерфейса (Vitest + jsdom).** Формы и компоненты отдельно от окна: проверка полей, подстановка категории по получателю, режим «скрыть суммы».
5. **Сквозные (настоящее окно).** Сценарии из [mvp-features.md](../product/mvp-features.md) по одному тесту на сценарий.
6. **Миграции.** Для каждой выпущенной версии в `crates/core/tests/fixtures/` хранится файл базы с данными. Тест открывает его новой версией и проверяет: копия сделана, данные на месте, балансы не изменились.

## Большой итоговый тест (перед выпуском 1.0)

1. **Полная регрессия:** `npm run check:e2e` на чистой машине, все тесты всех этапов.
2. **Сквозной «месяц жизни»:** один длинный сквозной тест проходит весь путь пользователя на чистой базе: мастер → счета в рублях и долларах → месяц операций → бюджет → кредит с платежами → напоминания → заметки → отчёты → сводка в Excel → резервная копия → восстановление в новую папку → все цифры совпадают с исходными.
3. **Обновление:** база версии 0.x с данными открывается версией 1.0, копия сделана, балансы и отчёты не изменились.
4. **Объём:** база на 10 лет учёта (около 100 000 операций): запуск, список операций, отчёт за год и сводка в Excel укладываются в заданное время (цель: экран открывается быстрее 1 секунды).
5. **Надёжность данных:** приложение принудительно закрывается посреди записи и посреди резервной копии; при следующем запуске база цела, недописанной копии в папке нет.
6. **Платформы:** сборка установщика для Windows (основная платформа), проверка на macOS и Linux.
7. **Ручная проверка владельцем:** короткий список из 15–20 действий на вашем компьютере (установка, первый запуск, обычный ввод операций, обновление), с местом для замечаний.

Итог большого теста записывается в отчёт: что проверено, что найдено, что исправлено.

| 1 | Если имя получателя набрано быстрее, чем пришли подсказки, категория не подставлялась | Подсказка применяется и при ответе ядра |

| 3 | Остатки на прошлую дату включали начальный остаток счёта, открытого позже этой даты | Тест `balances_on_a_date`; начальный остаток считается с даты открытия |

## Ограничения

- Сквозные тесты здесь работают на Linux (WebKitGTK). Windows-сборку можно проверять автоматически, когда подключим GitHub-репозиторий (GitHub Actions с Windows-машиной); до этого сборку для Windows проверяете вы по списку из пункта 7.
- Системные уведомления и трей сквозной тест не видит: тесты ядра проверяют, какие напоминания наступили и что уведомление отмечено отправленным, а сквозной — окно пропущенных напоминаний. Как уведомление и значок в трее выглядят в Windows, проверяется вручную.
